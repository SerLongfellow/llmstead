# LLMStead

Local React + Vite + TypeScript site for learning how LLMs work: train a tiny transformer from scratch in the browser and inspect every step. Long-term goal: a detailed tutorial covering the pipeline from tokenization → training → fine-tuning/RLHF → benchmarks.

## Commands
- `npm run dev` — dev server
- `npm run build` — `tsc && npm run pretrain-clip -- --check && vite build` (output in `dist/`, which is stale; rebuild). The middle step fails the build if the shipped CLIP no longer fits the engine, so a stale `public/models/clip-pretrained.*` blocks a deploy instead of shipping a VLM that silently falls back.
- `npm run gradcheck` — finite-difference check of the backprop
- `npm run clip:gradcheck` — the same check for the image + text model (both towers, projections, temperature; plain and multi-positive targets)
- `npm run clip -- --steps 5000 --every 500` — trains the image + text model like the app and prints loss, temperature and zero-shot accuracy (seen vs held-out combinations); options `--batch --lr --detail shape|position|full --fn ignore|multi --patch --dmodel --img-layers --txt-layers --no-held-out`. Step 0 is the untrained baseline.
- `npm run vlm:gradcheck` — gradient check of the vision-language model (projector + language model through image-token prefixes and an answer-only loss mask; phases 0 and 2) plus a one-batch overfit
- `npm run vlm -- --clip-steps 2000 --phase0 800 --phase1 800 --phase2 3000` — trains a CLIP, then the VLM phase by phase, and prints per-question exact-answer accuracy with the picture vs a blank picture, seen vs never-seen combinations. `--lr1 0.003` etc. per phase, `--every N`, `--phaseN 0` skips a phase, `--clip-steps 0` = untrained eyes. (A full run takes ~6 min.)
- `npm run pretrain-clip` — trains the ready-made CLIP the VLM uses by default (default settings, seed 1, 6k steps, ~7 min) and writes `public/models/clip-pretrained.{json,bin}`; commit both. `npm run pretrain-clip -- --check` (~1 s) loads the shipped files into the current engine and fails if they no longer fit or their zero-shot scores moved by more than 3 points. **Re-run the script whenever the CLIP's architecture, defaults or tower code change.**
- `npm run bench` — times a training step, a forward pass and one matmul (default + bigger config); run before/after engine changes
- `npm run evals` — trains every sample dataset like the Train tab (seeded, default model) and prints its benchmark at 2k/8k steps with per-case outputs; `npm run evals -- math-logic --steps 8000,16000` for one dataset. Run it after editing a dataset or benchmark suite. (Takes a few minutes.)
- `npm run export-gguf -- math-logic --steps 8000 --out x.gguf` — trains like evals and writes the GGUF the Train tab exports; `--check` also writes `x.gguf.check.json` (this engine's tokens and per-position probabilities for a few prompts) for comparing against llama.cpp.

## Deployment
**Every push to `main` goes live at https://llmstead.com** (usually within a minute or two), so treat a push as a publish.
- Hosted as a Cloudflare Worker named `llmstead` (static assets), built by Cloudflare Workers Builds from this GitHub repo. Build status shows up as a "Workers Builds: llmstead" check on each commit.
- Build settings live in the Cloudflare dashboard (there is no Wrangler config in the repo). The build runs `npm run build`, which includes the shipped-CLIP check; `esbuild` is a direct devDependency because that check (like the other scripts) bundles with it. A failed build doesn't deploy: the previous version stays live. Build failures show as a failed "Workers Builds: llmstead" check on the commit; Cloudflare can also publish build events to a Queue (Event Subscriptions, free plan) for Slack/email alerts via a small Worker (template: cloudflare/templates workers-builds-notifications-template). `.nvmrc` pins Node 22 for the build.
- `www.llmstead.com` is attached to the Worker too, and a zone Redirect Rule 301-redirects it to `https://llmstead.com` (keeps path and query).
- The site is fully static, so there are no server costs or secrets; the only recurring cost is the domain.
- SEO / link previews: `index.html` has the meta description, canonical URL, Open Graph + Twitter tags, and a plain-text summary inside `#root` for crawlers without JavaScript (React replaces it on mount). `public/` holds `robots.txt`, `sitemap.xml` and `og-image.png` (1200×630, rendered from an HTML mockup with headless Edge). The Worker serves the app for unknown paths with a 200 (SPA fallback), so missing files don't 404.

## Layout
- `src/engine/` — hand-written, dependency-free ML code (intentional: it's meant to be read)
  - `tensor.ts` — `MatrixMath`: matmul, transpose, softmax (+causal mask), layerNorm (no gain/bias), GELU. Plain `number[][]`. The hot loops (`matmul` especially, ~half of training time) look up rows once outside the inner loop (~4× faster matmul in V8 than plain `C[i][j]` indexing), so keep it that way. `zeros` stays `new Array(n).fill(0)`: a push-built version was faster in Node but ~40% slower in Chrome. Measure with `npm run bench`, but confirm engine changes in the browser too.
  - `block.ts` — one pre-LN transformer block (`blockForward`/`blockBackward`, with a `causal` flag), shared by the GPT and the image + text model. Moving it out of `transformer.ts` changed no numbers (bit-identical losses and gradients on a seeded run) and no speed.
  - `transformer.ts` — `MicroTransformer`. **Pre-LayerNorm** blocks, GPT-2 layout (LN → attention → residual add, LN → MLP → residual add, final LN before the head), no biases and no LN gain/bias. Was post-LN until the GGUF export; v1 autosaves are post-LN weights, so they keep settings but drop the model (`outdatedModel`). Inspection fields: `norm1Output` (what attention reads), `afterAttention`, `norm2Output` (what the MLP reads), `blockOutput`. `inspectForwardPass` captures every intermediate for the visualizers. `computeGradients` (backprop), `trainStep`, `evaluateLoss` (forward-only, for validation), `setOptimizer`. Throws if `dModel % numHeads !== 0`. Opt-in `PrefixOptions` (`prefix` rows placed before the tokens at positions 0..P−1, plus `lossMask` over text positions) on `computeGradients`/`evaluateLoss`/`inspectForwardPass`; `computeGradients` also returns `dPrefix`. Without them a pass is bit-identical to before (checked with a seeded loss/gradient fingerprint).
  - `optimizer.ts` — `Optimizer` (SGD with L2, AdamW with decoupled weight decay), per-named-matrix state.
  - `bpeTokenizer.ts` — character-level BPE with merge history (no pre-tokenization; merges can cross word boundaries).
  - `datasets.ts` — 4 small sample datasets + `splitDataset()` (last ~15% held out, cut at a paragraph/line break).
  - `generate.ts` — `sampleToken` (greedy when T ≤ 0.1) and `generateContinuation`, which does **token healing**: it backs up over the prompt's last token and constrains the first new tokens to regenerate that text. Needed because the BPE has no pre-tokenization, so spaces/indents merge into the *next* token in training ("1" | " + 1" | " = 2"), and prompts ending in "= " or "\n    " would otherwise leave the model on a token it rarely saw there.
  - `gguf.ts` — `exportGguf`: writes the model as a GGUF v3 file (`general.architecture = gpt2`, float32) for llama.cpp / Ollama. Projections are transposed (GGUF/PyTorch store one row per output), Q/K/V are concatenated into `attn_qkv`, biases are zeros and LN weights ones. The vocabulary uses llama.cpp's SentencePiece mode (`tokenizer.ggml.model = llama`, spaces as ▁, score = −merge step, no BOS/space prefix) because its GPT-2 BPE pre-splits words and would never form cross-word merges; 256 `<0xXX>` byte-fallback tokens are appended with `<UNK>`'s embedding and head column. The position table is padded to 4096 rows (later positions reuse the last trained row) and `gpt2.context_length` says 4096 (`llmstead.trained_context_length` holds the real one): llama.cpp asserts on positions past the table, and contexts are never as small as the model (apps default to thousands; llama.cpp rounds any context up to 256, so even Ollama with `num_ctx 16` ran a 256-token slot). `tokenizer.chat_template` joins non-system messages as plain text (for LM Studio / llama-server chat; node-llama-cpp rejects templates that drop messages). Verified with node-llama-cpp 3.22 (identical tokenization, probabilities within ~5e-4) and Ollama 0.35.1, which runs llama.cpp server inside it (`ollama create` from the modal's Modelfile works; `/api/generate` with `raw`, `logprobs` gives the same top token on 17/17 prompts, |Δp| ≤ 1e-2). Quirks found: llama.cpp asserts on 0 layers (`ExportModal` blocks it); Ollama trims a prompt that fills `num_ctx`; and since apps keep a KV cache instead of re-reading the last `contextWindow` tokens like the playground, text degrades once prompt + reply pass the window, so the instructions cap replies at `contextWindow` tokens. LM Studio instructions (`lms import`) are untested.
  - `benchmarks.ts` — prompt→expected-answer suites per dataset; `runBenchmarkSuite` greedy-decodes and labels each case `seen` vs `held-out` by checking the actual training text. `answerMatches` requires a whole-word match ("44" does not pass for "4").
- **Two model modes**, switched in the navbar (`ModeSwitch`, remembered in localStorage `llmstead.mode`): Text · GPT (everything below), Images · CLIP and Images → Text · VLM (see the Vision + Language section); `ModelMode` = `gpt | clip | vlm` (an old saved `vision` maps to clip, or vlm if `llmstead.visionStage` was `describe`). `App` renders `Site`, which keeps the workbenches mounted (inactive ones hidden with `display: none`, so training continues; a pulsing dot on another mode's button shows it) and owns the shared footer. Both image modes live in one lazy-loaded `VisionWorkbench` (its own chunk, built the first time either is opened), since the VLM borrows the CLIP; it renders one `<main>` per model, each with its own tab state. The Export button only shows in GPT mode.
- Tabs, in order (`TABS` in Navbar.tsx): Start here (`StartView`: intro, the 3-step path, suggested experiments) → ① Set up → ② Train → ③ Look inside (the Pipeline) → What's next (`WhatsNextView`: static explainer of the stages after pre-training: scale-up, SFT, preference/RL tuning, evals, deployment; content lives in its `STAGES` array). Each step has a dismissible `GuideStrip` (what to do + Next button; hidden state in localStorage `llmstead.hideGuides`, re-enabled from Start here).
- `src/components/` — one component per tab: `SetupView` (numbered sections: 1 Data, 2 Tokenizer/vocab size, 3 Architecture, all of which reset the model, plus a sticky parameter breakdown), `PipelineView`, `TrainingDashboard` (dataset shown read-only; owns the mid-training settings: learning rate and optimizer) with `BenchmarkPanel` inside. `ExportModal` (opened by the navbar's Export button, state in App): GGUF download, then tabs with run instructions for Ollama (Modelfile), LM Studio and llama.cpp (choice remembered in localStorage `llmstead.exportApp`), with an editable model name (default `llmstead-<dataset id>`, cleaned to Ollama-safe characters) used for the file, `FROM` line, commands and `general.name`; download disabled while training runs, since the page's weights lag the worker's.
  - `PipelineView` — the whole forward pass as a strip of stage cards (text → tokens → embeddings → blocks → probabilities → next token) with mini heatmaps; click a stage for its full detail view (read-only BPE `MergeHistory`, embedding/prediction tables, per-head attention via `AttentionGrid`, Q/K/V scores), click a token to follow its row through every stage. Re-runs inspection on mount so it reflects the latest weights.
  - `GoDeeper` — shared "Go deeper:" row of outbound links, used in the Pipeline's explainers and What's next.
  - `ScaleComparison` (bottom of Setup) compares the model to published architectures in `src/engine/referenceModels.ts` (GPT-2, GPT-3, Llama 2/3/3.1); undisclosed commercial models appear only as a context-window range. The Setup sliders cite them too; scale comparisons are deliberately kept to Setup.
  - `EmbeddingSpace` (inside the Embeddings stage) — token math (`a + b − c`, nearest by cosine; multi-token terms are averaged, quote a term to keep spaces), nearest neighbours of the followed token, and a 2D PCA map of the vocabulary (`pca2` in `src/engine/pca.ts`, also used by the vision map). It reads a **snapshot** of `wTokenEmbed` taken per run, because training mutates the live table in place (memos keyed on it would never refresh). Shared chip/cosine helpers live in `tokenUi.tsx`.
- **Autosave** (`src/persistence.ts`): one IndexedDB record (db `llmstead`, store `autosave`, key `latest`) holding settings, selected/custom datasets, the Pipeline prompt, training history, the tokenizer's vocabulary, and `MicroTransformer.exportState()` (weights + optimizer memory as `Float64Array`s; `importState` validates every shape before writing). `App` loads it once before rendering `Workbench`; the save is used only if the rebuilt tokenizer has the **same vocabulary** (a site update that changes a dataset invalidates old saves, which then show a "couldn't be restored" note). Saves every 10 s when something changed, on pause, and on tab hide/pagehide. A restored trained model opens on the Train tab with a "Welcome back" banner and a Start fresh button. Bump `SAVE_VERSION` if the record's shape changes. Fails softly in private windows (the Train tab says so).
- `src/App.tsx` — owns state, including the dataset list (built-ins + custom text added in Setup). Tokenizer is rebuilt via `useMemo` from the selected dataset + `config.vocabSize` (the *target* vocab, set only by Setup's vocab slider; the tokenizer is deliberately not retrainable elsewhere, since a new vocabulary means a new model); never mutate it in place. The model is memoized **only on shape-changing settings**, so the learning rate and optimizer can change without resetting weights. Children get `effectiveConfig` (vocabSize = real tokenizer vocab).

## Vision + Language (CLIP → VLM)
A tiny CLIP: the engine in `src/engine/vl/`, the UI mode in `src/components/vl/`. Two navbar modes: Images · CLIP and Images → Text · VLM (a tiny LLaVA-style VLM built on the CLIP), each with its own Start here / Set up / Train / Look inside / What's next. (An earlier in-page Match/Describe switch was dropped: a second navigation axis under the tabs was confusing.) The VLM's Start page shows whether the CLIP is trained enough, with a jump to its Train tab; the CLIP's Start and What's next point on to the VLM. Actions (VLA) are out of scope.
- `shapes.ts` — seeded 24×24 pictures: one of 4 shapes × 4 colours × 2 sizes, centred in one of 9 cells of a 3×3 grid (±1 px jitter), so position words are always fair and balanced. `patchify`.
- `captions.ts` — captions from labels at 3 detail levels (`shape` "a red circle", `position` "+ at the top left", `full` "+ small/big"), 2 phrasings; `captionKey` = the facts stated (same key = interchangeable captions). Word-level tokenizer over a fixed 22-word `VOCAB` (unknown words are dropped and reported). `DEFAULT_HELD_OUT`: green triangle and yellow cross never appear in training.
- `clip.ts` — `MicroClip`: image tower (patch embedding + position → non-causal blocks → final LN → mean-pool → `wProj` → L2-normalize) and text tower (same over words); learned `logScale` temperature (init 1/0.07, capped at 100); symmetric InfoNCE. `falseNegatives`: `ignore` (plain CLIP) or `multi-positive` (same-key pairs in the batch all count as right, soft targets). `inspectImage` also gives a per-patch "where does this caption match" score (each patch's final-LN row through `wProj`, a heuristic). `exportState`/`importState`/`clone`.
- `clipData.ts` — defaults (`DEFAULT_CLIP_CONFIG`: d 32, 4 heads, 2 image layers, 1 text layer, mlpRatio 2, dEmbed 16, patch 8), `sampleBatch`, fixed `testPairs`, `gridPairs` (8 pairs that differ from their neighbours by one fact), `zeroShot` (best of every possible caption; per-fact accuracy).
- `clipTraining.ts` + `clipWorker.ts` — same chunk/worker protocol as the GPT's trainWorker; the worker also runs the zero-shot tests every 250 steps (`EVAL_EVERY`) and posts them. Not autosaved.
- UI (`VisionWorkbench`): Start here (two-tower diagram, experiments) → ① Set up (samples, caption detail, held-out toggle, patch size, model size; all reset the model) → ② Train (kept mounted; batch size, lr and false negatives change mid-run; live 8×8 caption × picture similarity grid; loss + temperature chart; zero-shot chart per fact, seen vs never-seen combos) → ③ Look inside (text-to-image search, one picture with caption-match or per-patch attention overlay and its top captions, text tower `AttentionGrid` with `causal={false}`, PCA map of pictures + the 16 colour/shape captions; trained vs untrained) → What's next (real CLIP, SigLIP, uses, the VLM step).
- Findings (`npm run clip`, defaults: batch 16, lr 1e-3; ~65–100 ms/step in Node depending on machine load, ~12 steps/s in the browser worker when the machine is quiet). At 4k steps: whole caption right 96% on seen combinations vs 63% on never-seen ones (the held-out number swings 50–80% between checkpoints); colour and position ~100%. **Patch size matters a lot**: an 8 px patch is exactly one grid cell; at 6 px (shapes cut across patches) shape was 54% at 5k steps while the loss was already 0.21. That's the contrastive shortcut: in a batch of 16, colour + position already separate almost every pair, so the loss stops pushing for shape. Colour-only captions (`--detail shape`) force shape (67% at 3k, 6 px), but never-seen combos lag badly there (20–28%).
- **VLM engine:** `vlmData.ts` (word vocab = CLIP `VOCAB` + question words, `?`, `:`, `<end>`; 6 tasks: describe / colour / shape / where / size / is-there (half true, false ones differ by one fact, never naming a held-out combo); example = question + answer + `<end>`, `lossMask` on the answer only). `vlm.ts` `MicroVlm`: frozen vision = a `MicroClip` copy (`patchFeatures`: per-patch final-LN rows) → projector MLP (`proj.w1` → GELU → `proj.w2`, LLaVA-1.5 style) → a `MicroTransformer` LM (word vocab, contextWindow = patches + 18, d 32 / 2 layers / 2 heads by default). Its own `Optimizer` steps only what the phase trains (`PHASE_TRAINS`): 0 text only (image slots are zeros, LM learns), 1 align (projector only, describe only), 2 instruction-tune (both). `answersCorrectly` scores greedy exact-match in one teacher-forced pass. `vlmTraining.ts` (`vlmEvalSet`: 32 seen + 16 held-out pictures × every task, each scored with the picture and with a blank background picture) + `vlmWorker.ts` (same protocol; sends a baseline eval at each phase start).
- **Ready-made eyes** (`src/engine/vl/pretrained.ts`): the whole CLIP (33k weights) as little-endian Float32 in `public/models/clip-pretrained.bin` (~130 KB, not in the JS bundle) plus a manifest (format `PRETRAINED_FORMAT`, config, data settings, training recipe, matrix names/shapes in `getParameters()` order, zero-shot scores of the Float32-rounded weights). `fetchPretrainedClip` runs the first time the VLM mode opens; `unpackWeights` checks format, config keys, every matrix name/shape and the exact byte length before writing anything, because a missing file comes back as the SPA's HTML with a 200. On failure the VLM falls back to `encoder: 'clip'` and Setup says why. The VLM's `encoder` is `pretrained` (default) | `clip` | `random`.
- **VLM UI:** `VisionWorkbench` keeps a frozen *copy* of the CLIP (`visionCopy`, taken when the VLM mode is first opened or via Setup's "Take a new copy"; below 1,000 CLIP steps Setup suggests "Train the CLIP now", which switches to the CLIP mode's Train tab and starts it) or the untrained CLIP as the encoder. `VlmSetupView` (encoder, tasks with live examples, LM size), `VlmTrainView` (phase cards with start/switch, pipeline diagram showing frozen/learning parts, per-phase lr defaults `PHASE_LR` 0.001/0.003/0.001, loss coloured by phase, "Does it look?" chart per task with picture vs blank vs never-seen, latest-test table, an honest note that skipping phases barely matters here), `VlmInsideView` (picture strip + blank, question with presets, greedy answer as clickable words; per word: attention from the choosing position onto the patches as an overlay, attention over the question words, top-5 next words; optional nearest word per image token; full causal `AttentionGrid` over ▣1…▣9 + words). Phase switching is disabled while a run is active (avoids racing the worker's final weights). Not autosaved.
- **VLM findings** (`npm run vlm`, CLIP 2k steps, batch 8; ~40–55 ms/step in Node, ~20 steps/s in the browser worker). Phase 0 (800): picture ≈ blank ≈ prior (colour ~25%). Phase 1 at lr 0.001 learns nothing in 800 steps; at **0.003** describe goes 0 → 31% with the picture (0% blank) over 2k steps while every other question stays at prior: alignment teaches describing, not answering. After phase 2 (3k): describe 91%, colour 100%, shape 94%, where 100% with the picture vs 0/31/16/13% blank; never-seen combos: colour 88%, where 100%, shape 56%, describe 13%. Size stays near chance (66% vs 59% blank): the default CLIP captions never mention size, so its frozen features barely keep it. "Is there a X Y?" stays near 50%. **Skipping phases 0 and 1** (phase 2 only, 3k steps) is as good or better (describe 97%, shape 94%, size 88%): the tiny LM has nothing to protect, which the Train tab says.

## Backprop
`computeGradients` in `transformer.ts` is a full manual backward pass (per-op rules for LayerNorm, GELU and softmax live in `tensor.ts` as `*Backward`). `trainStep` clips to global grad-norm 1.0, then sends **every** parameter through `this.optimizer.step()`. `npm run gradcheck` (esbuild-bundles `scripts/gradcheck.ts`) compares every matrix against central finite differences (`src/engine/gradCheck.ts`, whose `checkGradientsOf` works for any model); expect relative error ~1e-7. Consider making the derivation a tutorial tab.
- With real gradients, AdamW lr ≈ 0.001 works best; the app default is 0.001 and the Train-page slider is linear 0.001–0.05 (a log-scale slider is a good follow-up; SGD likely needs 0.05–1, untested).
- Training windows are sampled at random from the train split (not slid sequentially).
- Continuous training (Start/Pause) runs in a **Web Worker** (`src/engine/trainWorker.ts`): the page sends it `model.exportState()` + the train/val tokens, it runs `trainChunk` (`src/engine/training.ts`, shared with the page) in ~100 ms chunks, posting one chart point per chunk and its weights ~1/s and on stop, which the page `importState`s into its own model (so Look inside / generate / benchmarks see weights ≤1 s old). Workers aren't throttled in background tabs or blocked by page repaints: in a hidden page ~2.7× the old on-page loop, with ~60 ms worst page stall vs ~360 ms. `workerBusy` stays true until the final weights arrive (Step disabled, App's autosave waits); run ids drop late messages after a model change, and Reset ignores in-flight chart points. Learning rate / optimizer changes are forwarded mid-run. If `new Worker` fails, the old on-page tick loop (`TICK_BUDGET_MS`/`TICK_GAP_MS`) is the fallback. Validation runs every 200 steps (`VAL_EVERY`) on ≤32 fixed windows. Step and slow motion still train on the page (exactly one step).

## Other notes / ideas
- The default dataset is math-logic (first in `SAMPLE_DATASETS`). Each dataset has a `samplePrompt` (via `samplePromptFor`, which falls back to the first line for custom text) used as the Pipeline input and the generation seed when that dataset is selected.
- Shakespeare dataset is Coriolanus 1.1 + 1.3 (~15k chars, typed from memory, verse lines joined per speech); its validation split starts at scene 3.
- Training tokens at vocab 120: math ~11.1k, Q&A ~8.0k, Shakespeare ~9.3k, code ~4.9k. math-logic is fully generated (`buildMathLogicText`); code and Q&A are hand-written text plus templated variations (`buildCodeText`, `buildQaText`), all with seeded shuffles. Each non-Shakespeare dataset keeps its original lines first (so benchmark "seen" cases stay in the train split) and deliberately omits the benchmark's held-out strings, including as substrings ("32 + 1 = 33" contains "2 + 1 = 3"; math has a final `HELD_OUT` filter). Keep it that way when editing datasets or benchmarks.
- `withRepeatedCore` scatters `CORE_COPIES` (10) extra copies of each dataset's seen-case items through the first 80% of the text (never the validation tail): a fact that appears once is statistically invisible to a model this small. Shakespeare can't be padded, so its seen cases are phrases that already recur (counts in the suite's comments). Typical `npm run evals` at 8k steps (seen, held-out): math 4/8, 1/5 (arithmetic is slow for this model); Shakespeare 4/5, 2/3; code 4/4, 3/3; Q&A 3/3, 2/2.
- Prompt boxes (`PromptInput`) are textareas: a single-line `<input>` strips newlines, and prompts like the Q&A one need them. Enter = newline, Ctrl/⌘+Enter = run.
- **Slow motion** (Train tab toggle, `SlowMotionPanel`): runs one step at a time via `runDetailedStep` (captures per-position predictions and errors, per-layer gradient norms, and the same window re-checked after the update) and replays it in 5 stages: Sample, Forward, Compare, Backward, Update (`STAGE_MS` timings). Start auto-plays; when paused, the panel's button steps through stages. The fast loop is skipped while slow motion is on.
- The Training Dashboard stays mounted (hidden with `display: none`) so its loss history survives tab switches and training keeps running in the background; the navbar shows a pulsing dot on Train while it runs. The other tabs are conditionally rendered.
- "Reset" on the training chart clears history only; weights re-init when the architecture, tokenizer or dataset changes.
- Future direction discussed: keep this in-browser toy engine for mechanics, and add a separate real-model tier (Python + PyTorch/Hugging Face backend, or transformers.js/WebGPU) for importing base models, LoRA/DPO fine-tuning, and benchmarking. Reuse the same visualizations across both.
